## Part 3 — agent-driven file deletion (the one standing rule that changed)

By explicit user request, Friday can now delete a single file from the IDE's open workspace — the first and only exception ever made to the "no delete tool" policy. It is deliberately narrow and gated in code, not just by prompting:

**Two new tools, always used as a pair:**
- `ide_analyze_file_for_deletion(path)` — read-only. Reads the file's full content and searches the rest of the workspace for anything that still references it (by filename, and for `.py` files, by its dotted import path too). Returns a report: the content, every matching reference elsewhere (file:line:snippet), and a verdict ("NOT clearly dead" if referenced, "appears unused" if not). Friday is instructed to relay this to the user — what the file contains, whether it looks safe to remove — and ask for confirmation before doing anything else.
- `ide_delete_file(path)` — only succeeds if `ide_analyze_file_for_deletion` was just called for this *exact, unchanged* file (content hash checked). Calling it without a fresh matching analysis is refused outright, by code, not just instruction — so Friday cannot skip the read-and-check step even if it tried. The file is never permanently destroyed: it's moved into a hidden `.friday_trash` folder inside the workspace (invisible in the Explorer, search, and workspace tree — added to the same `SKIP_DIRS` list as `.git`/`node_modules`), timestamped, so a wrong call can always be undone by moving it back out by hand.

**What's enforced in code (not just the system prompt):**
- No deletion without a prior analysis of that exact path.
- No deletion if the file's content changed since it was analyzed (catches edit-then-delete races).
- No deletion if the analysis is more than 30 minutes old (must re-analyze if it goes stale).
- Only individual files, never folders — `ide_analyze_file_for_deletion`/`ide_delete_file` both reject a directory path outright. Deleting a whole folder is still human-only, via the IDE's own right-click Explorer menu, which still permanently deletes (unchanged, untouched).
- Deletion always soft — moved to `.friday_trash`, never unlinked for real.

**What still depends on the model behaving correctly (same trust model as every other tool here):** actually waiting for the user's explicit "yes, delete it" after hearing the analysis, rather than assuming consent. There's no separate human-in-the-loop UI gate for this one (unlike `ide_close_tab`'s real blocking modal) — it relies on `personality.md`'s explicit instruction plus the two-call code gate above. Voice commands containing "delete"/"remove" already also get Task 35's cross-check confirmation layer for free (both words are in `CONFIRMATION_ACTION_VERBS`), since a misheard deletion is exactly the kind of command that layer exists to catch.

Friday's natural-language IDE control is now **55 tools total** — 9 always-on general tools + 46 Agent-Mode-only tools.

## Part 4 — minimize-to-pill (window-control change, not a new tool)

By explicit user request: the titlebar's minimize button (previously an inert placeholder while agent-controlled, same as close/maximize — see the "winctrl_zone" comment in `ide/ide.py`) is now always live, and does something custom instead of a normal OS-level minimize.

**Behavior:** clicking minimize eases the whole IDE window down into Friday's floating circle (reusing the existing close-animation's shrink/fade, `_play_close_animation`), then — instead of destroying it — replaces it with a small pill-shaped `MinimizedPill` window positioned just under the circle, connected to it by a thin vertical line drawn in the same small window. Hovering the pill (after a short debounce, so a quick mouse pass-through doesn't trigger it) speaks the panel's name aloud through Friday's own configured voice — `APP_NAME` ("IDE") — via a new `agent_overlay.py` bridge (`agent_tools.set_speak_label_handler`/`_AgentHost.speak_label`, mirroring the existing chat-handler bridge). A plain click on the pill restores the real window, growing back out of the circle to exactly the size/position it had before minimizing.

**Scope decision (user didn't answer the clarifying question, so a judgment call was made and is called out here):** there is only one separate top-level window in this app besides the circle itself — the IDE — so "add the minimize button to all panels" was interpreted as that one window, not each of the IDE's internal docked panels (Explorer/Terminal/Chat/Search/Source Control) individually floating out near the circle, which would require a much larger floating-panel subsystem and was never separately requested once clarification was skipped.

**Graceful fallbacks, not just the happy path:**
- No circle on screen at all (e.g. the circle-rect provider fails, or `ide.py` is running standalone via `python ide.py` with no Friday overlay process) → falls straight back to the original plain OS-level minimize (`minimize_window`/`iconify`), never crashes, never fabricates a pill with nowhere real to anchor to.
- True per-pixel window shaping (so only the line + pill are ever visible, nothing rectangular around them) only exists on Windows Tk (`-transparentcolor`); everywhere else it falls back to a small opaque panel in the IDE's own theme color, same shapes, just with a visible background behind them.
- Minimizing twice in a row is a no-op (never two pills stacked on each other); destroying the main window (e.g. Friday turning Agent Mode off) while minimized automatically destroys its pill too, via Tk's normal parent→child destroy cascade (`MinimizedPill` is a child `Toplevel` of the IDE window) — no orphaned windows left on screen.

## Part 6 — real app panels: Chrome/Notepad/Calculator become Friday's own, minimizable like the IDE

**What was actually asked for (corrected from Part 5's initial misread):** Friday should really launch real native applications on command — not fake them inside the editor — but the moment he opens one, it becomes one of *his* tracked panels, exactly the way the IDE itself already is since Part 4: minimizable into a small pill tucked under his floating circle, restorable with one click, closeable. "Minimize all tabs" with the IDE, Chrome, and Notepad all open should collapse all three into pills under the circle at once, because by "tab" in that context the user means "one of the top-level things Friday has open," not a browser-internal tab or an unrelated window Friday had nothing to do with.

**Clarifying questions asked and answered before building this:**
1. *What does "minimize" actually do to a real external app's window?* Answer: a hybrid — the real app genuinely minimizes to the taskbar (a real, robust `ShowWindow(hwnd, SW_MINIMIZE)`, not a fragile attempt to reparent a foreign GPU-rendered window like Chrome's into a custom shape), **and** a custom pill still appears under the circle as Friday's own visible handle on it; clicking the pill restores the real window.
2. *How much content control, beyond open/minimize/close?* Answer: "basic" — a URL for Chrome (opens a new tab of the same running Chrome, via its own well-known single-instance command-line remoting — no extra automation needed), and pre-filled/typed text for Notepad.
3. *Which apps?* Answer: "a short known list" — Chrome, Notepad, Calculator for now.

**What was built:**
- New module `app_panels.py` — `AppPanelManager`, deliberately decoupled from the coding IDE's own Tk-thread machinery (see agent_tools.py's `_tk_worker_loop`/`_TkThreadBridge` for how much hard-won care *that* needs — this doesn't touch any of it). Runs its own small dedicated Tk thread, started lazily the first time a panel is actually minimized, purely to host pill widgets — reuses `ide.py`'s existing, already-generic `MinimizedPill` class as-is rather than duplicating it.
- Three small pluggable backends, all real by default and all fake-able for testing without a real Windows desktop or real Chrome/Notepad/Calculator: `RealLauncher` (subprocess launch, Windows-first with macOS/Linux fallbacks), `RealWindowBackend` (raw-`ctypes` win32 window find/minimize/restore/close — no pywin32 dependency, matching how the rest of this codebase already talks to win32 elsewhere; a safe no-op everywhere else), `RealTyper` (optional `pywinauto`-based keystroke injection into an already-open Notepad, Windows-only, clearly reports when it isn't available rather than pretending).
- New always-on tools (work whether or not Agent Mode/the coding IDE is on — opening Chrome has nothing to do with coding): `open_app(name, url=, content=)`, `list_open_apps()`, `minimize_app(which)`, `restore_app(which)`, `close_app(which)`, `type_in_app(which, text)`. `which`/`"all"` use the same ambiguous-name-matching convention as Part 5's `ide_close_tab`: an exact or unique substring match acts, zero or multiple matches refuse and explain instead of guessing.
- The IDE itself is folded into this same vocabulary by `agent_tools.py` (not by `app_panels.py`, which knows nothing about the IDE): `list_open_apps()` shows "IDE" alongside any open external apps; `minimize_app("all")`/`restore_app("all")`/`close_app("all")` include it by calling the IDE's own existing `minimize_to_pill()`/`restore_from_pill()`/`agent_mode_off()`; `minimize_app("ide")` etc. target it directly. Closing the IDE does not touch separately-tracked Chrome/Notepad panels and vice versa — the two subsystems' lifetimes are independent by design.
- `ide_run_terminal_command`'s docstring now points at `open_app` instead of carrying a blanket "never launch GUI apps" warning.
- `personality.md`'s panels section was rewritten to describe this correctly: real apps are really opened, then tracked as Friday's own panels; `ide_list_open_tabs`/`ide_close_tab` stay a separate, narrower concept (tabs *inside* the code editor) that shouldn't be conflated with these top-level panels; ambiguous "minimize"/"close" commands should check `list_open_apps`/`ide_list_open_tabs` and ask, except a bare "minimize" with nothing else open to confuse it with (still unambiguous, per Part 4).

**Known, honestly-flagged limitation:** true per-pixel reparenting of a foreign app's window (making Chrome itself visually become the little pill, the way the IDE's own window can since it's Friday's own Tk toplevel) was deliberately *not* attempted — it's a well-known source of instability for GPU-compositing apps like Chrome. The pill is Friday's own small proxy window with a label and click target; the real app window minimizes/restores normally alongside it.

## Part 7 — real window embedding: Notepad/Calculator actually live inside Friday's own panel frame

**Correction to Part 6's "known, honestly-flagged limitation":** Part 6 shipped and was delivered to the user, who immediately rejected it on sight: the real apps were only ever tracked via a separate real window plus a small proxy pill, and what was actually wanted was for the opened app's real content to be visually *inside* a Friday-drawn panel ("THE OPENED APP SHOULD BE INSIDE THE PANEL" — the user's exact words, given in response to a follow-up clarifying question after the rejection). So Part 6's deliberate choice not to attempt true window reparenting is now superseded for Notepad and Calculator specifically — this part adds that embedding for real.

**Clarifying questions asked and answered before building this:**
1. *Chrome's known reparenting risk* — Chrome is the textbook case where `SetParent`-based reparenting breaks GPU-compositing rendering (blank/black frames, lost input, flicker). Answer: Chrome stays a separate, non-embedded window (Part 6's design, unchanged for Chrome only); Notepad and Calculator get truly embedded.
2. *Where the embedded panel opens on screen.* Answer, user's exact words: "IT OPENS ANYWHERE ON SCREEN WITH A DEFAULT SIZE, FOR EXAMPLE THE IDE WAS ALREADY OPENED TO VIEW AND NOTEPAD WAS THEN OPENED THE IDE STILL STAYS AT THE CENTER OF THE SCREEN WHILE NOTEPAD OPENS A SMALL PANEL AT ANY CORNER OF THE SCREEN. VISUALLY SMALL." — i.e. each embedded panel opens independently, small, in a free screen corner, without moving or overlapping whatever else (like the IDE) is already open.

**What was built:**
- `EmbeddedAppPanel(tk.Toplevel)` in `app_panels.py` — a borderless (`overrideredirect(True)`) frame styled with the IDE's own color theme (`ide.py`'s `C` dict — `tabbar`/`fg`/`fg_dim`/`hover`/`danger`/`editor`, for visual consistency with the rest of Friday's UI) with a custom draggable titlebar (app-name label, minimize "—" and close "✕" labels with hover states — overrideredirect windows have no native titlebar/drag of their own, so both are hand-built) and a `slot` frame filling the rest, whose real native window id (`slot.winfo_id()`) is the actual embedding target. Opens at a default 480×360 size, positioned into one of the four screen corners (24px margin) based on how many panels are already embedded, computed straight from `winfo_screenwidth()/winfo_screenheight()` rather than any shared default-root global (this module and the IDE each run their own independent Tk root on their own thread, so a shared-default-root shortcut would be unreliable here). `set_resize_callback()` keeps the embedded app's real window size in sync whenever the slot itself is resized (`<Configure>`).
- `RealWindowBackend` gained `embed(parent_hwnd, child_hwnd, width, height)` and `resize_embedded(child_hwnd, width, height)`. `embed()` strips the child window's native `WS_POPUP`/`WS_CAPTION`/`WS_THICKFRAME`/`WS_SYSMENU` styles, adds `WS_CHILD`, then calls `SetParent` and an initial resize — all raw `ctypes` (`GetWindowLongPtrW`/`SetWindowLongPtrW`/`SetParent`/`SetWindowPos`), no pywin32 dependency, matching how this backend already talks to win32 elsewhere. Both methods are safe no-ops (return `False`) anywhere but Windows, or on any failure, so callers always have a clear "did it actually work" signal to fall back on.
- `AppPanelManager` gained `EMBEDDABLE_APPS = {"notepad", "calculator"}` (Chrome deliberately excluded) and `_try_embed(key, rec)`, called once a newly-opened embeddable app's real window handle is discovered: builds an `EmbeddedAppPanel` on the panel-host's Tk thread, attempts `backend.embed(...)` into its slot, and on any failure destroys the half-built frame and leaves that panel exactly as un-embedded as Chrome always is — same tracked-separate-window behavior, not a hard error. On success it wires the resize callback, and explicitly re-checks whether the panel was minimized while embedding was still in flight (an async race: `_discover_and_embed` runs hwnd discovery and embedding on a background thread, so the user's "minimize that" can land before it finishes) — the freshly-built frame is withdrawn immediately rather than shown-then-hidden if so.
- `_minimize_one`/`_restore_one`/`_close_one` each gained an `if rec.get("embedded")` branch: for an embedded panel, minimize/restore/close act on the Friday-owned frame itself (`withdraw()`/`deiconify()`/`destroy()`) instead of the real window backend, since the real window is now a child and has no independent taskbar presence of its own; for anything not embedded (Chrome, always, or a fallen-back embeddable app), the existing Part 6 hybrid real-OS-minimize-plus-pill path is unchanged.

## Part 8 — fixing a real bug: Part 7's embedding silently never fired on a real Windows PC

**What was reported:** Part 7 was delivered and tested on a real Windows PC — both Notepad and Calculator opened as their own normal windows, with no small Friday panel appearing at all, and no error output anywhere. That meant `_try_embed` was never even getting a real window handle to work with, or an exception was happening somewhere and being swallowed by one of the broad `except Exception` guards without a trace.

**Root cause, found and confirmed:** Part 7's hwnd-discovery (`find_hwnd_for_pid`) matched a newly-launched app's real window purely by `GetWindowThreadProcessId(hwnd) == our subprocess's pid`. That assumption is simply false for both apps being embedded, on modern Windows:
- Windows 11 resolves a bare `notepad.exe` through an **App Execution Alias** (`%LocalAppData%\Microsoft\WindowsApps\notepad.exe`, a reparse point) that launches a legacy stub process, which then hands off to the real, separately-packaged modern Notepad app. The pid Python's `subprocess.Popen()` gets back is the stub's — not the pid that ends up owning the actual window. This is independently documented (confirmed via a Stack Overflow thread describing exactly this: `pi.dwProcessId` from `CreateProcessW("notepad.exe", ...)` never matches the Notepad pid shown in Task Manager, with Microsoft's own guidance being to disable the alias to make them match).
- Calculator has the same shape of problem via `ApplicationFrameHost.exe` hosting a separate packaged `CalculatorApp.exe` process — already flagged as a risk in Part 7, but it turns out to affect Notepad too, which Part 7 had assumed was safe.

So `find_hwnd_for_pid` was enumerating real windows, finding none owned by the pid it was given, and returning `None` after its timeout — with zero exceptions anywhere, which is exactly the "nothing happens, no panel, no error" symptom reported. `_try_embed` was never even reached.

**The fix:**
- `RealWindowBackend.find_hwnd_for_pid` is superseded by **`find_hwnd_for_launch(pid, title_hint, before_hwnds, timeout=8.0)`**: a snapshot of every currently-visible top-level window is taken (`snapshot_top_level_hwnds()`) *before* `RealLauncher.launch()` is even called; after launching, any window that's newly appeared since that snapshot is a candidate — a direct pid match wins outright (keeps working exactly as before for ordinary, non-packaged apps like Chrome), and failing that, a case-insensitive substring match against each candidate's window title (`"notepad"`/`"calculator"`/`"chrome"`, added to `KNOWN_APPS` as `title_hint`) is used instead, which still correctly identifies the real window even when it's owned by a different, OS-managed process than the one actually launched.
- **No more silent failures.** Every failure path in the embedding pipeline now records a plain-English reason into `rec["embed_note"]`, which shows up directly in `list_open_apps()` next to that panel (e.g. "Notepad (open) — couldn't find its window to embed it into a panel, so it's running as its own separate window"). This covers: the window never being found at all, `EmbeddedAppPanel` construction raising, and `backend.embed()` itself raising or returning failure — previously all of these were swallowed by bare `except Exception` guards with nothing surfaced anywhere, which is what made Part 7's actual failure undiagnosable from the report alone ("still not working," no console errors). Now the same failure is self-diagnosing: asking Friday "what do you have open" surfaces the real reason without needing a terminal.
- `agent_tools.py`'s `open_app`/`list_open_apps` docstrings were updated to describe the title/snapshot-based discovery and the new self-diagnosing fallback notes.

**Caveat, honestly disclosed (still not independently verified on a real Windows machine by this delivery, since the author has no direct access to one):** the title-substring heuristic is a reasonable, commonly-used fix for exactly this class of problem, but its correctness still ultimately depends on the real window's actual title at the moment it's found containing the expected word ("Notepad"/"Calculator") — which is true for the default/English UI of both apps, but could misbehave for a non-English Windows install or a window title customized some other way. If embedding still doesn't work after this fix, `list_open_apps()` will now at least say *why* (or, if it says nothing is wrong and genuinely no panel appears, that would point at a different bug — e.g. in the `SetParent`-based reparenting itself rather than discovery — and should be reported back with that `list_open_apps()` text).

## Part 9 — unified window management: one pool, one pill stack, a 3-panel cap, and real maximize/restore

**What was asked for** (user's own framing): treat the IDE and every `app_panels.py` panel (Chrome/Notepad/Calculator) as *one single pool of panels*, not the IDE plus a separate app-panel subsystem — "all panel are all the same." Specifically:
1. A `maximize_app(which)` command that resizes/repositions a panel to exactly the IDE's own current window bounds (swap-style — it visually takes over that screen position), with only one panel "active"/maximized at a time (maximizing one demotes whatever was previously maximized back to its own normal size).
2. Restoring a minimized panel always comes back at its small default size — restore and maximize are separate, explicit actions; restoring never silently re-maximizes.
3. Every minimized panel — IDE included — shares one single, non-overlapping vertical pill stack under the circle (IDE's pill closest to the circle if minimized first, next-minimized panel's pill below it, and so on), instead of the IDE and `app_panels.py` each computing pill positions independently (which could overlap).

**Architecture decision:** `agent_tools.py` already constructs both `IDEApp` and `AppPanelManager` with the *exact same* `_AgentHost` singleton (`_AGENT_HOST`). That single shared object is therefore where all of this cross-subsystem bookkeeping lives — new methods/state added directly to `_AgentHost` and to module-level globals in `agent_tools.py`, called identically from `ide.py` and `app_panels.py` via their existing `self._agent_host` references. Neither `ide.py` nor `app_panels.py` needed to import the other, or even know the other exists.

**What was built:**
- **Unified pill stacking.** `agent_tools.py` gained a module-level `_MINIMIZED_STACK` (ordered list of panel keys, earliest-minimized closest to the circle) plus `_stack_add_and_index`/`_stack_remove_and_reflow` helpers, and `_AgentHost` gained three dispatch methods: `get_pill_slot(key)`, `release_pill_slot(key)` (returns the reflow list for everything still minimized), and `reposition_pill(key, slot_index)` (routes to `_ide_app.reposition_pill_to_slot()` for `"ide"`, or `_panel_manager.reposition_pill()` for anything else). `ide/ide.py`'s `MinimizedPill` gained `STACK_GAP`/`STACK_STEP` class attributes (the single source of truth for pill spacing, now shared by `app_panels.py` too instead of its own separate `PILL_GAP` constant) and a `reposition(circle_bottom)` method that moves an already-shown pill to a new slot without rebuilding it. `IDEApp._show_pill()` asks for a slot via `get_pill_slot("ide")` and offsets its y-position by `slot_index * STACK_STEP`; `IDEApp.restore_from_pill()` calls `release_pill_slot("ide")` and reflows everything the call reports, synchronously, *before* its own grow-back-out animation starts (so the stack is never left with a stale middle-of-stack gap even mid-animation). `app_panels.py`'s `_minimize_one`/`_restore_one` go through new `_pill_slot_for`/`_release_pill_slot_for` helpers that delegate to the shared `agent_host` when one is wired up, falling back to the old local count-based scheme otherwise (e.g. a test harness with `agent_host=None`).

## Part 10 — a third embedding failure report, this time root-caused at the ctypes level (not another guess)

**What was reported, after Part 9's delivery was tested on a real Windows PC:** "still not working the note pad isnt opening just a panel named note pad please review and fix for all instances to work professionally." This is the third time embedding Notepad has been reported broken on real Windows (Part 7's original attempt, Part 8's pid/title-discovery fix, and now this one). Both Part 7 and Part 8 shipped a fix believed at the time to be the real cause and each was later contradicted by a real-Windows retest — so this time, before writing any code, the whole of `RealWindowBackend` was re-read line by line specifically looking for anything that could produce *exactly* this symptom: the panel frame itself appearing (so `EmbeddedAppPanel` construction and `SetParent` both "work") while the real app's content inside it never renders (so it looks like an empty panel labelled with the app's name) — which is a different, more specific symptom than Part 8's "nothing happens at all."

**Root cause, found via ctypes-semantics code review (no real Windows machine available to this environment, so this is reasoned from documented ctypes/Win32 behavior, not reproduced locally — see the honest caveat below):** every Win32 call in `RealWindowBackend` was made through bare `ctypes.windll.user32.SomeFunction(...)`, with no `argtypes`/`restype` ever declared on any of them. Undeclared ctypes functions default to treating every argument and the return value as a 32-bit signed `c_int`. That default is silently wrong for `GetWindowLongPtrW`/`SetWindowLongPtrW`, whose real values are pointer-sized (`LONG_PTR`) and, more importantly here, for a plain *window style* value: an ordinary, completely normal top-level window's style (e.g. Notepad's own, combining `WS_VISIBLE | WS_CLIPSIBLINGS | WS_CAPTION | WS_SYSMENU | ...`) very commonly has its top bit set. A default-prototyped `GetWindowLongPtrW` call turns that into a **negative** Python int instead of the correct large positive one. The embedding code then mixed that negative value with the plain positive hex mask constants (`WS_POPUP = 0x80000000`, etc.) in bitwise AND/OR/NOT arithmetic meant to strip the window's title bar/border bits and add `WS_CHILD` — bitwise ops on a sign-corrupted value can silently produce the wrong resulting style instead of raising any error. Critically, **`SetParent` itself doesn't care what the style value is** — it reparents the window regardless, and reports success either way. So the panel frame shows up exactly as built (that part was never broken), `SetParent` "succeeds," but the reparented Notepad content inside it fails to actually display correctly because its style bits came out wrong — which is precisely "just a panel named notepad," the exact phrase in the report.

**The fix — not a narrow patch, a full hardening of every win32 call in the class (the "for all instances... professionally" ask):**
- A new cached `RealWindowBackend._user32()` builds a single `ctypes.WinDLL("user32", use_last_error=True)` with explicit, correctly-sized `argtypes`/`restype` declared for **every** function the class calls: `GetWindowLongPtrW`/`SetWindowLongPtrW` as pointer-sized `c_ssize_t` (not `c_int`); `SetParent`/`GetParent` as `wintypes.HWND`; and `SetWindowPos`, `MoveWindow`, `GetWindowRect`, `ShowWindow`, `SetForegroundWindow`, `PostMessageW`, `IsWindowVisible`, `GetWindowTextLengthW`/`GetWindowTextW`, `GetWindowThreadProcessId`, and `EnumWindows` all given their real Win32 signatures. Every method in the class (`minimize`, `restore`, `close`, `embed`, `resize_embedded`, `get_window_rect`, `move_resize`, `bring_to_front`, `_enum_visible_windows`) now goes through this one correctly-prototyped handle instead of the old bare `ctypes.windll.user32.*` calls — this is what makes the fix cover Notepad and Calculator equally (both go through the exact same `embed()`), rather than special-casing one app.
- `embed()` itself: the style value read back from `GetWindowLongPtrW` is immediately normalized to unsigned 32-bit (`& 0xFFFFFFFF`) before any bitmask logic touches it, eliminating the sign-corruption at its source. A new `_to_long_ptr_arg()` helper converts a style value to the correct signed form only if actually needed (32-bit Python/Windows only — a genuine no-op on every realistic 64-bit target, verified by a direct unit test below).
- **`SetParent`'s report of success is no longer trusted blindly** — `embed()` now calls `GetParent(child_hwnd)` immediately afterwards and confirms it actually equals the intended parent before declaring success, since `SetParent` returning non-NULL is not, by itself, 100% proof every app accepts the reparent.
- **The content is now explicitly forced to display**, not just assumed to once reparented: `SetWindowPos` gained `SWP_SHOWWINDOW`, and `ShowWindow(child_hwnd, SW_SHOW)` is called explicitly right after reparenting/resizing.
- **Much better self-diagnosis, per the "professionally" ask:** `embed()`'s return signature changed from a bare `bool` to an **`(ok, reason)` pair**. On failure, `reason` is now a specific, real Win32 error string via a new `_last_error_text()` helper (`ctypes.get_last_error()` + `ctypes.FormatError()`, e.g. `"SetParent failed (WinError 5: Access is denied.)"`), instead of the old generic "couldn't be embedded into its panel" note with no further detail. `AppPanelManager._try_embed()` was updated to unpack this tuple and put the specific reason straight into `rec["embed_note"]`, so `list_open_apps()` now surfaces the exact Win32-level reason if embedding ever fails again — which matters given two previous "fixed it" claims on this exact area turned out to be wrong; if this one is *also* wrong, the next report should come with actual diagnostic text instead of another guess.

**Honest caveat (unchanged in kind from every earlier part, repeated deliberately given the history here):** this environment has no real Windows machine to execute this code on, so the fix is backed by code review against documented ctypes/Win32 behavior (the default-prototype 32-bit `c_int` assumption and its sign-corruption consequences for `GetWindowLongPtrW` are well-established, widely-documented ctypes pitfalls — this is not a novel guess the way Part 8's title-matching heuristic partially was), not by a local reproduction-then-fix cycle. **If Notepad or Calculator still don't render their content after this fix, please copy/paste the exact `embed_note` text from `list_open_apps()` (or run `test_embedding_standalone.py` and send its printed output) — with a specific Win32 error string now available, any further round has concrete data to work from instead of another blind guess.**

## Part 12 — the first-opened panel takes the full screen, centered; every later one stacks down the left edge; maximize is a real position swap

**What was asked for** (user's own framing, refined over three `ask_user` rounds into a locked spec): "if any panel is opened first the default maximized size (the ide panel size) is what it should take whether its the notepad or the ide or any other panel from now on the first panel Friday opens takes the screen at center." Worked out into a complete, concrete layout:
1. The IDE's own current size is the reference "maximized/full-screen" size every panel can fill.
2. Whichever panel is opened *literally first in the whole running session* — the IDE, Notepad, Chrome, or Calculator, whichever one that happens to be — takes that full-screen, centered slot automatically, the instant it opens. This is a one-time event: it never re-triggers later even if everything is closed and something new is opened afterward. (Exception, explicitly preserved: if the IDE itself is that first panel, it keeps its own existing near-fullscreen-but-offset-from-the-circle placement rather than switching to some new "centered" formula — the only actual behavior change for the IDE-as-first-panel case is that it's now also flagged as the maximized/active panel.)
3. The 2nd/3rd/4th panels opened after that land in three fixed smaller "side slots" stacked down the left edge of the screen, in order: top-left, then center-left (vertically centered), then bottom-left.
4. A 5th panel (once all three side slots are full) evicts the oldest (top-left) one to a minimized pill under Friday's circle, the center-left and bottom-left ones shift up to close the gap, and the new panel lands in the now-empty bottom-left slot.
5. Explicitly maximizing a panel (`maximize_app`) is a full position *swap*, not "promote one, demote the other to some generic spot": the panel being promoted takes the center slot, and whatever was previously maximized takes over *exactly* the side slot the newly-promoted one just vacated.
6. The IDE itself is no longer exempt from being resized into a side slot — Part 9's old assumption that "the IDE's own window size never changes, it IS the reference size" is explicitly superseded: the IDE can now be the thing sitting in a small side slot while something else is maximized, and `maximize_app("ide")` swaps it back out exactly like any other panel.

**Architecture decision:** the same `_AgentHost`-as-shared-hub pattern Part 9 established gets extended, not replaced. `AppPanelManager` gained a `_decide_placement(key)` method that delegates to a new `_AgentHost.get_panel_placement(key)` (falling back to `(None, False, "")` — i.e. "no opinion, use your own old default" — if no `agent_host` is wired up, so a standalone `AppPanelManager` in a test harness is unaffected), and a `_release_panel_slot_for(key)` delegating to a new `_AgentHost.release_panel_slot(key)` the same way. All the actual placement *policy* — the once-ever full-screen rule, the three side slots, the 5th-panel eviction, the maximize swap — lives in `agent_tools.py`, the one module that already knows about both the IDE and every `app_panels.py` panel; `ide.py` and `app_panels.py` still don't know about each other.

**What was built:**
- **`ide/ide.py`:** `compute_agent_controlled_bounds(sw, sh)` was pulled out of `IDEApp.__init__` into its own free function — the fixed formula for "the IDE's own near-fullscreen layout," computable without a live `IDEApp` instance (the IDE might not even be open right now, or might currently be shrunk into a side slot). `IDEApp.__init__` gained an `initial_bounds=None` override parameter: when given, it's used verbatim instead of either of the two existing branches (agent-controlled formula vs. the plain-`python ide.py` centered-default), so a non-first-panel IDE opens directly into its assigned side slot with no flash of the "wrong" size first. A new `resize_to_bounds(x, y, w, h)` method lets the IDE be physically moved/resized after the fact (relaxing/restoring `minsize()` around the request exactly like the existing open/close pop animations already do, plus the same set-twice-after-`update_idletasks()` firm-geometry trick `EmbeddedAppPanel` uses) — the mechanism `maximize_app`/the side-slot system uses to promote/demote the IDE's own window. It also explicitly cancels any still-in-flight open/close pop animation first (see the race below).
- **`app_panels.py`:** `move_to`/`move_to_slot`/`maximize_to` were factored apart on both panel classes so a plain reposition (`move_to`) is shared by the one maximize slot and the three side slots alike, differing only in whether `is_maximized` ends up set. `AppPanelManager` gained `screen_size()` (real screen dimensions via its own hidden Tk host, with a 1920×1080 fallback), `maximize_panel(key, bounds)`/`place_in_side_slot(key, bounds)` (both now also stamp the result onto `rec["placement_bounds"]`/`rec["placement_is_maximized"]` — see the race fix below), and `unmaximize_panel(key, bounds=None)`. `open()`, `_open_custom_panel()`, `_discover_and_embed()`, and `_try_embed()` were all rewired to thread a `(bounds, is_maximized, note)` triple all the way through, from the moment `_decide_placement()` is consulted at the top of `open()` down to wherever the panel actually ends up (synchronously for Notepad's custom panel; asynchronously, once the real window is found and optionally embedded, for Chrome/Calculator).
- **`agent_tools.py` — the actual placement policy**, all new module-level state/functions: `_SIDE_SLOTS` (ordered list of up to 3 keys occupying the side slots), `_ever_opened_first_panel` (flips to `True` exactly once, forever, the first time any panel opens in the process's life), `_ide_reference_bounds()` (always formula-computed via `compute_agent_controlled_bounds`, never read from the IDE's live window — the specific change that means **maximizing a non-IDE panel no longer requires the IDE to be open at all**, superseding Part 9's old restriction), `_side_slot_bounds(index)` (top-left/center-left/bottom-left, reusing `EmbeddedAppPanel.DEFAULT_W/DEFAULT_H/MARGIN` — i.e. every panel type, IDE included, uses the same uniform small side-slot size), `_side_slot_add(key)`/`_side_slot_remove(key)` (append-with-eviction-if-full, and remove-with-reflow, respectively), `_place_new_or_restored_panel(key)` (the once-ever-full-screen-or-else-next-side-slot decision, called from both `open_app()`/`agent_mode_on()` for a fresh open and `restore_app()` for a restore — replacing Part 9's old `_enforce_panel_cap`), and `_release_panel_slot(key)` (the reverse, called whenever a panel is minimized or closed). `maximize_app()` was fully rewritten around an explicit swap: it captures the target's current side-slot index *before* removing it from `_SIDE_SLOTS`, promotes the target to `_ide_reference_bounds()` (via `IDEApp.resize_to_bounds` for `"ide"`, `AppPanelManager.maximize_panel` for anything else), then re-inserts whatever was previously maximized at that *exact* captured index and physically moves it there — a literal swap between the two specific panels involved, with no live IDE-window dependency anywhere in the call path. A panel already maximized refuses a redundant re-maximize with a plain "already the maximized, active panel" message instead of silently repeating the work.
- **A real concurrency race, found and fixed along the way (not a user report — surfaced by this part's own new tests):** Chrome/Calculator's real-process embedding runs on a background discovery thread (`_discover_and_embed`/`_try_embed`, unchanged in spirit since Part 7) that can take a non-trivial, variable amount of wall-clock time (actual `SetParent`/`embed()` work). If `maximize_app()` (or a side-slot reflow) landed on that same panel key *while* that background thread was still mid-flight, the thread's own delayed completion would finish by stamping the panel's frame back to wherever it had been *when the thread started*, silently undoing the newer placement decision moments later. Fixed by having the discovery thread re-read the panel's live `rec["placement_bounds"]`/`rec["placement_is_maximized"]` twice more after its own initial read — once right before actually constructing the embedded frame, and once more at the final commit point right after a (possibly slow) real `SetParent` call — physically re-correcting the frame's position if anything changed in between, rather than trusting values it captured before the slow part even started.
- **A second, related race, also found via the new tests:** Agent Mode's own open-pop animation (easing the IDE's window from the circle up to its real size) takes 340ms and is still running in the background when `agent_mode_on()` returns — it only waits for the window to exist, not for the animation to finish. A `maximize_app("ide")` call landing in that window could have its `resize_to_bounds()` call immediately overwritten by the animation's own next already-scheduled `.after()` tick, still easing toward its *original* target. Fixed by having `resize_to_bounds()` explicitly cancel any in-flight animation's scheduled job (`self._geom_anim_job`) and clear `self._anim_active` before applying its own geometry, the same cancel-the-old-job mechanism `_animate_geometry()` already uses internally when one of its own calls supersedes another.
- **Unilateral design decision, flagged here rather than hidden:** all three side slots use the existing uniform `EmbeddedAppPanel.DEFAULT_W`/`DEFAULT_H` (480×360) for every panel type, including a demoted IDE — not a larger, IDE-specific side-slot size. This was not confirmed with the user; the IDE will look fairly cramped at 480×360 compared to its usual near-fullscreen self. Easy to change later (one constant, or a per-key override in `_side_slot_bounds`) if that turns out to look wrong in practice.

**Known, honestly-flagged limitation:** same caveat as every real-process-embedding part before it (7/8/10) — the Calculator-specific embedding path (and the new discovery-thread race fix riding on top of it) has not been exercised against a real Windows OS window, only against this sandbox's fake `RealWindowBackend`-shaped test double. The IDE's own placement/animation-cancellation code, and Notepad's custom panel, have no such caveat — they're pure Tk and were fully exercised exactly as they'll run on the user's real PC.

### Issue #1 — the pill-click bug

**Investigation:** extensive static review of `MinimizedPill`'s construction/`tag_bind`/`on_restore` wiring in both `ide.py` (the IDE's own pill) and `app_panels.py` (every other panel's pill) found no late-binding/shared-closure mistake — each pill is a fully independent Toplevel bound to its own `on_restore` callback, each resolving to a single, specific key (never `"all"`). A synthetic Tk-level repro (fake launcher/window-backend, `agent_mode_on()` + two apps + `minimize_app("all")`, then simulating an actual click on whichever pill ended up topmost) confirmed the click/restore logic itself is correctly isolated per-pill — clicking one pill in a 3-pill stack restored only that one panel, every time, across repeated runs.

That same repro did surface two real, concrete, previously-unreported bugs along the way, both now fixed:

- **Pill *ordering* race:** `minimize_app("all")` always asks the IDE to minimize first, then every app_panels.py panel — but the IDE's own minimize is *animated* (a ~260ms shrink-to-circle pop) while app panels minimize *instantly*, with no animation. The app panels' synchronous stack-slot claims could race ahead and grab slots 0/1 before the IDE's own (correctly first-requested) claim landed, leaving the IDE's pill stacked *last* instead of closest to the circle. Fixed two ways in `agent_tools.py`'s `_minimize_ide_panel()`: it now reserves "ide"'s slot in the shared stack *synchronously*, the instant it's called (`_stack_add_and_index` is idempotent, so `_show_pill()`'s later claim just reuses the same reserved slot) — and it now also polls (bounded, ~1s) for the actual pill *widget* to finish appearing before returning, so a `restore_app` landing in the gap between "slot reserved" and "pill actually exists" can no longer see a false "the IDE isn't minimized" and skip releasing that slot.
- **Stale pill-stack-slot leak on close-while-minimized:** closing a panel (or the IDE) *while it was minimized* (a pill showing) released its side-slot/maximize ledger entry but never its separate pill-stack ledger entry — `_close_one()` (`app_panels.py`) and `on_ide_closed()` (`agent_tools.py`) both had this exact gap. The pill *widget* itself was destroyed correctly, but the key stayed phantom-registered in the shared `_MINIMIZED_STACK` forever, throwing off every other still-minimized panel's reported slot index from then on (a permanent gap in the stack, not an overlap — `_MINIMIZED_STACK` enforces unique keys, so two different panels can never actually collide on the same slot). Fixed by having both places also call `release_pill_slot`/`_stack_remove_and_reflow` (with the usual reflow of everything below it) whenever the thing being closed was minimized.

A defensive one-shot guard was also added to `MinimizedPill._on_click` itself (ignores any click received after the first one, since a pill is about to destroy itself) as cheap insurance against any stray repeat event firing `on_restore()` twice for the same single pill.

**Honest limitation:** none of the above, on its own, reproduces "one click restores *everything*" — only an ordering/bookkeeping problem. `MinimizedPill` uses Windows' `-transparentcolor` for true per-pixel window shaping (so only the line+pill shape are ever clickable, nothing rectangular around them); on Linux (this sandbox) that call raises `TclError` and it falls back to a plain opaque window instead, which this environment can't exercise the Windows-specific behavior of at all. If this is still observed after this fix, it's most likely something about that Windows-only layered-window click-hit-testing behavior rather than the placement/bookkeeping logic covered here — please report back with the exact repro (how many pills were stacked, whether literally every one of them visibly animates back open from one single click, and whether the IDE is involved) so it can be targeted specifically.

### Issue #3 — generalized "active panel" pulsing border

A new `ide.py` class, **`_ActiveGlowAnimator`**, drives a slow (1.6s period), smooth, cosine-eased pulsing-brightness animation in a dedicated violet (`#a855f7`, used nowhere else in the app, so it never gets confused with Friday's own busy/ok/error status colors or a plain idle-white border) — plain composition (not a mixin), since `IDEApp` and the `tk.Toplevel`-based app panels don't share a common ancestor: each owns one instance and hands it a `set_color(hex)` callback that paints its own particular flavor of border (`IDEApp` recolors its native Tk `highlightbackground`/`-color`; `EmbeddedAppPanel`/`CustomNotepadPanel` recolor the thin white margin around their titlebar/slot via `configure(bg=...)`, the same mechanism that already drew their plain white border).

Every panel type now has a `set_active_panel(active: bool)` method (`IDEApp`, `EmbeddedAppPanel`, `CustomNotepadPanel`) that starts/stops its own animator and repaints immediately. For the IDE specifically, Friday's own existing conversational-state border color (`set_friday_status` — blue/green/red while busy/succeeding/failing) always takes priority over the pulse: the violet animation only actually paints while Friday's live status is idle, replacing what used to be a flat static white border in that state; the moment Friday's status goes non-idle, the pulse's own paint calls become no-ops (it keeps ticking in the background so it resumes instantly once idle again) and the busy/ok/error color shows exactly as before.

**Wiring (all centralized, no panel type needed to know about any other):** a new `agent_tools._apply_active_panel_flag(key, active)` is called from every one of the three places `_maximized_panel_key` can change — `_place_new_or_restored_panel` (the session's first-ever panel), `_release_panel_slot` (minimize or close of the currently-active one), and `maximize_app`'s swap (the newly-promoted panel turns on, whatever it displaced turns off) — plus one extra IDE-specific hookup in `_tk_worker_loop` (right after the real `IDEApp` instance is actually constructed) to cover the one case `_apply_active_panel_flag` necessarily can't: the IDE being the session's first-ever panel, decided (and attempted) *before* the IDE's own Tk thread/instance even exists yet. `EmbeddedAppPanel`/`CustomNotepadPanel`'s own `maximize_to()`/`move_to_slot()`/`restore_default()` methods also call `set_active_panel` directly themselves (the same two/three places `is_maximized` already gets flipped), so the border updates correctly even for calls that don't go through `agent_tools.py` at all (e.g. a standalone/no-agent_host test harness).

**Honest limitation:** Chrome is the one app type with no Friday-drawn frame at all (a real, unwrapped OS browser window — `EMBEDDABLE_APPS = {"calculator"}` only, Notepad is always Friday's own custom panel) — this is a pre-existing gap, not a new one: Chrome never got the plain white border treatment in the first place, so there's no border for the active-panel pulse to paint onto either. Every panel type that *can* show a border (the IDE, Notepad, Calculator) now shows this new one correctly.

## Part 15 — the embedded chat panel's freeze/no-response bug, root-caused and fixed, plus a new standing scope restriction on that panel

User report: "the chat box in the ide seems to have a bug or something, talking to Friday through it actually freezes or doesn't go through," plus a new standing rule: that chat box must never be able to tell Friday to open a tab, minimize the IDE, or issue any other panel-management command — strictly coding tasks (writing/running code) only.

**Root cause (confirmed by direct reproduction, not just static reading):** `agent_overlay._ide_chat_ask()` executes on the IDE's own dedicated Tk thread (`ChatSidePanel._send()` calls it directly) — a real OS thread that pumps no Qt event loop of its own. It used to build, wire up (`.succeeded.connect(on_ok)`/`.failed.connect(on_fail)`), and start its `AIWorker` right there, on that thread. A `QThread` subclass's own signals, connected to a plain Python callback (not a bound `QObject` slot, which is what `on_ok`/`on_fail` are — plain closures), get delivered via a queued call targeting wherever the `QThread` *object itself* was constructed — not wherever its `run()` method actually executes, and not wherever `.connect()` was called from either. Building the worker on the Tk thread means that queued delivery is silently dropped forever: `on_ok`/`on_fail` never fire at all, no error, no warning, no crash — exactly a "freezes or doesn't go through." Proven directly: a minimal `QThread` built on a plain background thread, whose signal is connected to a plain function, simply never calls it, confirmed with print-instrumented isolated repros before touching any production code. A second, narrower instance of the identical class of bug also existed one layer deeper: *inside* `on_ok`/`on_fail` (on the rare occasions they ran at all, e.g. for the circle's own normal voice/typed path, which has always correctly built its `AIWorker` on the Qt main thread), `QTimer.singleShot(2000, ov._finish_responding)` was being scheduled from `AIWorker`'s own background thread — also silently dropped for the same no-event-dispatcher reason, confirmed by making the dropped callback `app.quit()` itself and watching `app.exec()` hang forever.

**The fix, in `agent_overlay.py`:**
- A new persistent `_MainThreadInvoker(QObject)` (a `Signal(object)` connected via `Qt.QueuedConnection` to a slot that calls the received callable), constructed once in `main()` right after `QApplication(sys.argv)` — guaranteeing its own thread affinity is the real Qt main thread regardless of which thread later calls it — plus a module-level `_on_qt_main_thread(fn)` helper that emits through it (a safe no-op if the invoker hasn't been built yet, e.g. in a test that doesn't call `main()`).
- `_ide_chat_ask()` now routes every Qt-touching step through this helper: the initial `ov._enter_state(STATE_LOADING)` call (the Tk→Qt crossing), and — the actual fix for the freeze — the entire build/wire-up/start of the `AIWorker` itself, via a new `_start_worker()` closure passed to `_on_qt_main_thread()`. This guarantees the `AIWorker` QObject's own thread affinity is always the real Qt main thread, so its `succeeded`/`failed` signals reliably deliver `on_ok`/`on_fail` no matter which thread `_ide_chat_ask()` was entered from. `_settle()` (called from inside `on_ok`/`on_fail`, which now correctly run on the Qt main thread already) still wraps its body in `_on_qt_main_thread()` too, both for defense-in-depth and because it's the one place the once-dropped `QTimer.singleShot(2000, ...)` lives.
- `CircleOverlay._push_ide_status()` → `ide.py`'s `set_friday_status()` was a second, separate, pre-existing cross-thread violation found and fixed along the way (not the user's reported symptom, but directly adjacent to the exact code path under repair, and a genuine Tcl-interpreter safety issue, worse than Qt's graceful drops): it was calling straight into a Tk widget from whatever thread called `_enter_state()`, based on a stale comment claiming Friday and the IDE "share one process and one thread" — no longer true since the IDE moved onto its own dedicated Tk thread (`agent_tools._tk_worker_loop`/`_TkThreadBridge`, an earlier round's change). Fixed by routing through `agent_tools._post_on_main()` — the same fire-and-forget `_TkThreadBridge`-backed primitive `agent_tools.py`'s own app-panel code already uses for exactly this — instead of calling `app.set_friday_status(...)` directly. The stale comment (in both `agent_overlay.py` and `ide.py`) was corrected to describe the real three-thread architecture.

**The new standing scope restriction, in `agent_tools.py`:** a new `IDE_CHAT_TOOL_NAMES` (exactly the `ide_*` tools, nothing else — no `agent_mode_on/off`, no app/window-management tools, no web search/memory/calendar/plain-file tools) plus `get_ide_chat_gemini_tools()`/`get_ide_chat_tool_schemas()` (the trimmed lists actually handed to each provider) and a `call_tool(name, arguments, ide_scoped=False)` parameter that independently refuses to run anything outside that set — a defense-in-depth backstop in case a model ever requests a tool it was never even offered (Groq/Mistral's manual tool-calling loop can't rule this out the way Gemini's automatic function calling structurally can). `AIWorker.__init__` gained a matching `ide_scoped=False` parameter, threaded through to whichever provider actually runs; `_ide_chat_ask()` is the only call site that ever passes `ide_scoped=True`. The circle's own two call sites (`parent=self, summarize_only=True` for the voice-confirmation check, and the plain voice/typed path) are untouched and keep full tool access, exactly as before.

### The 2-minute unanswered-pause autonomy rule

A single-turn request/response model has no innate sense of wall-clock time passing after it replies, so the rule is split into two halves that meet in the middle:

- **The model's half (prompt-level, in `personality.md`):** a new bullet, right after the existing "pause and ask" policy, instructing Friday that a major-decision/external-action pause still can't block forever — if two minutes pass with no reply, proceed with the most professional option and say so — and, critically, to end any such pause with the literal control tag `{{AWAIT_DECISION}}` on its own line. - **The code's half (real engineering, in `agent_overlay.py`/`agent_tools.py`/`ide.py`):** a new `_extract_await_decision(text)` detects and strips the tag before it ever reaches speech, a chat bubble, or memory, and a new `_PendingDecisionTracker` class (one per conversation surface) arms a real `QTimer` for 120 seconds whenever the tag is seen. Two independent instances exist — `CircleOverlay._decision_tracker` for the floating circle's own voice/typed chat, and a module-level `_ide_chat_decision_tracker` for the IDE's embedded "Friday AI Chat" panel — so a pause on one surface never auto-resolves just because the *other* happens to see activity. A real new user message on a surface calls `.cancel()` on that surface's tracker (a generation-counter bump, not an actual `QTimer.stop()`, so it's safe regardless of call order); if nothing cancels it, the timer fires a synthetic, clearly-labeled "(System note, not from the user: ... no one answered ... decide and proceed)" prompt back through that exact same surface's normal AI pipeline, and the result is delivered the normal way for that surface — spoken aloud for the circle (`CircleOverlay._auto_continue_pending_decision` → `_on_query_submitted(..., is_auto_continue=True)`), or as a brand-new, unprompted chat bubble for the IDE panel.

The IDE-chat half needed one genuinely new piece of plumbing, in the opposite direction of the existing `host.ask(text, on_done)` call: nothing is "waiting" on an `on_done` callback when a 2-minute timer fires on its own, so there was no existing way for `agent_overlay.py` to push a message *into* `ide.py`'s `ChatSidePanel` out of band. ## Part 19 — the real "Friday isn't responding" bug: AI provider calls had no network timeout at all

User reported, live, after the previous part's update: asking Friday any question (Agent Mode off, just the floating circle, typed input) left it stuck "thinking" forever — several minutes, no reply, no error, nothing in the console. Diagnosed and fixed in the same turn as a real, pre-existing defect in the AI call layer itself, unrelated to the frontend-skill addition (confirmed first: Agent Mode being off meant none of that part's new tool code could even run, which narrowed the search to whatever *does* execute on every call regardless of Agent Mode — the three `_try_gemini`/`_try_groq`/`_try_mistral` provider calls in `agent_overlay.py`).

### Root cause, confirmed by reading the installed SDKs' own source rather than guessing

`genai.Client(api_key=GEMINI_API_KEY)` was built with no `http_options`, and `types.HttpOptions()`'s own default `timeout` is `None` — traced directly into `google-genai`'s internal request code, `timeout=None` is passed straight through to the underlying `httpx` call, and passing `None` to `httpx` explicitly *disables all timeouts* (different from not passing a timeout at all, which would use `httpx`'s own 5-second default). In plain terms: a Gemini call that connects but then gets no response — a stalled proxy, a VPN hiccup, a silently dropped connection, any of the ordinary ways a real network misbehaves — had nothing stopping it from blocking forever. No exception means no fallback to Groq/Mistral, no friendly error message, no automatic connectivity retry (Part 17's whole retry mechanism *requires* a caught, classified exception to arm) — just silence, which from the user's seat is indistinguishable from "it's broken." Groq's SDK turned out to already default to a bounded `Timeout(connect=5, read=60, write=60, pool=60)`, and Mistral's `httpx.Client()` (built with no explicit timeout) falls back to httpx's own 5-second default — both already finite, so Gemini (the first provider tried, per `run()`'s own call order) was the one actually capable of hanging indefinitely, and the most likely explanation for what was observed.

### The fix

A new `AI_REQUEST_TIMEOUT_SECONDS = 30` constant, next to the existing `RETRIES_PER_MODEL`/`RETRY_BACKOFF_SECONDS`. Wired into all three provider clients explicitly, for symmetry and because "already has *some* bound" isn't the same guarantee as "has the *same, deliberately chosen* bound": `genai.Client(..., http_options=types.HttpOptions(timeout=int(AI_REQUEST_TIMEOUT_SECONDS * 1000)))` (the field is milliseconds), `groq.Groq(..., timeout=AI_REQUEST_TIMEOUT_SECONDS)`, `Mistral(..., timeout_ms=int(AI_REQUEST_TIMEOUT_SECONDS * 1000))`.

A second, equally real problem surfaced while fixing the first: simply adding the timeout, on its own, would have *replaced* an indefinite hang with a *confusing* error — `httpx.ConnectTimeout`/`httpx.ReadTimeout`'s own `str()` is typically just the bare word `"timed out"`, which matches none of `_CONNECTIVITY_ERROR_MARKERS`' phrases (`"read timed out"`, `"connection timed out"`, etc. — all *longer*, differently-worded strings), and `httpx`'s timeout classes aren't subclasses of Python's built-in `TimeoutError` either, so `_looks_like_connectivity_error()`'s existing type check wouldn't catch them by type any more than by text. Confirmed directly (`httpx.Client(timeout=0.001).get(...)` against a non-routable address really does raise `ConnectTimeout` with `str(e) == 'timed out'`) rather than assumed. Fixed by adding `httpx.TransportError` (the shared base class behind `ConnectTimeout`/`ReadTimeout`/`ConnectError`/etc. in every httpx version this project depends on) to `_looks_like_connectivity_error()`'s type-check tuple, via a best-effort lazy `import httpx` (matching the rest of this function's and the provider methods' own lazy-import-optional-dependency style) — so a request that now times out at 30s gets the same friendly `🔌 No internet connection detected` message and the same automatic once-connectivity-returns retry (Part 17) as a hard connection failure already did, instead of a confusing generic `"⚠️ Gemini error: timed out"` dead end.

## Part 20 — "wasting a lot of time processing and responding": the Part 19 timeout fix needed a circuit breaker, not just a timeout

User reported, immediately after Part 19's fix: Friday no longer hangs forever, but now every single message — simple chat and coding tasks alike — takes 30-90 seconds to answer. Confirmed via direct questions this is the *same* underlying problem as Part 19, just now bounded instead of infinite: with multiple providers configured, `run()` always tries them in the same fixed order (Gemini, then Groq, then Mistral), and if one of them is reliably unreachable for this user specifically (a firewall/VPN/ISP route blocking just that one vendor while the rest of the internet works fine — Part 19's own fix means that failure now takes a bounded ~30 seconds instead of forever, which is strictly better, but it still pays that same ~30-second tax **on every single message**, every time, before falling through to whichever provider actually answers.

### The fix: a short per-provider circuit breaker

A provider's first failure always gets its full, honest attempt and timeout — this is never used to avoid trying a provider that might actually work. But the moment that attempt fails for a *connectivity* reason specifically (not a bad key, not a quota limit — those are a different problem and retrying them is actually pointless, not just slow), a `PROVIDER_SKIP_COOLDOWN_SECONDS = 90` cooldown starts for that one provider's name. Any message that arrives during that cooldown skips straight past it (near-zero cost) to the next configured provider, instead of re-discovering the same "still down" fact the slow way every time. A real success clears the cooldown immediately, so a provider that recovers mid-cooldown is tried again right away rather than waiting out whatever was left of it.

Implemented as three small module-level functions in `agent_overlay.py` (`_provider_recently_unreachable(name)`, `_record_provider_connectivity_failure(name)`, `_record_provider_recovered(name)`, backed by a simple `threading.Lock`-guarded dict, since `AIWorker` instances are short-lived — one per request — but this state needs to persist *across* them) plus a small `_attempt(name, try_fn)` closure inside `AIWorker.run()` itself that wraps all three existing `self._try_gemini`/`self._try_groq`/`self._try_mistral` calls identically, checking the breaker before calling and updating it based on the real outcome after. None of the three `_try_*` methods themselves needed to change — this is purely a `run()`-level concern, which is also the one place that already knows the fixed provider order and already classifies `CONNECTIVITY_ERROR_TAG in err`. A skipped provider's error slot is filled with a message that still carries `CONNECTIVITY_ERROR_TAG` (clearly worded as "skipped" rather than "just failed," for honesty/debuggability), so `run()`'s own existing "every provider failed the exact same way" collapsing logic from Part 17 still treats a skip identically to a fresh failure — which is the accurate outcome either way.

### Testing (Part 20)

## Part 21 — "Reached the tool-call limit before finishing": a real multi-file build needs far more than 5 tool-call round trips

User screenshotted the IDE's embedded "Friday AI Chat" panel: asked it to "BUILD ME A FRONTEND CODE OF AN ECOMMERCE WEBSITE," got back *"Reached the tool-call limit before finishing — try rephrasing or breaking the request into smaller steps."* Traced directly to `AIWorker._run_tool_loop()` — the manual multi-turn tool-calling loop shared by Groq and Mistral (Gemini doesn't use this at all; passing it plain Python functions turns on the SDK's own automatic function calling, which runs its whole loop internally inside one network call) — which had a hardcoded `max_iterations=5` that had never actually been exercised by a real multi-file build before now.

### Why this specific request was always going to hit it, and why it's partly a direct consequence of this session's own earlier change

A real ecommerce frontend build needs, at minimum: reading/listing the workspace to see what's already there, then a create-file-plus-write-file pair for every file (`index.html`, a stylesheet, a script, probably more than one page) — easily 10-20+ tool-call round trips for anything beyond a single-file toy page. Worse, Part 18 (this session's own frontend-skill addition) tells Friday to call `ide_get_frontend_skill()` as the very first step of any real frontend build — which is correct, valuable guidance, but it also means a genuine frontend build now spends one of an already-too-small 5-iteration budget before any actual file gets touched at all. The combination (a hard 5-call ceiling + guidance that spends one call before real work starts + a task that inherently needs far more than 5) made this close to inevitable the first time anyone tried a real build through Groq or Mistral specifically.

### The fix

Two new named constants in `agent_overlay.py`, replacing the bare hardcoded `5`: `TOOL_LOOP_MAX_ITERATIONS = 10` (the general ceiling — ordinary chat tool use like a memory lookup or a calendar check rarely needs more than one or two round trips, so this is already generous headroom) and `TOOL_LOOP_MAX_ITERATIONS_IDE = 40` (used specifically when `self._ide_scoped` is true — i.e., the request came through the IDE's own embedded chat panel, which by its own existing design is strictly for coding/build work). Both `_try_groq()`'s and `_try_mistral()`'s call sites now pass `TOOL_LOOP_MAX_ITERATIONS_IDE if self._ide_scoped else TOOL_LOOP_MAX_ITERATIONS` instead of relying on `_run_tool_loop`'s old bare default; that default itself was also updated to reference `TOOL_LOOP_MAX_ITERATIONS` rather than a disconnected literal `5`, so anything that ever calls it without an explicit override still gets a sensible, intentional number. A loop that never stops requesting tools even at 40 still terminates and reports the same clear "reached the limit, try breaking it into smaller steps" message as before — this change raises the ceiling, it doesn't remove it; a model that's genuinely stuck in a runaway loop still gets caught and reported rather than running forever.

### Testing (Part 21)
This exact code path had **no prior test coverage at all** — confirmed by searching the whole `dev_tests/` suite for any reference to `_run_tool_loop`/`max_iterations` before this part, finding none. New dedicated `dev_tests/test_tool_loop_iteration_limit.py` (15 checks, 4 parts), deliberately its own lean file (no Tkinter/`ide.py` dependency, unlike the panel-status suite) since this is pure `agent_overlay.py` logic:
- **A** — both new constants exist, the IDE ceiling is more than double the general one, and it's comfortably above 20.
- **B** — direct unit coverage of `_run_tool_loop()` itself via a small scripted fake `create_fn`: a model that never requests a tool returns immediately; a few genuine tool calls followed by a real answer succeeds and stops exactly when the model stops asking for tools (never wastes iterations); each tool result is actually fed back into the growing conversation, not discarded; a model that never stops requesting tools is cut off at exactly the given ceiling (not before, not after) and produces the limit message.
- **C** — the two *real* call sites, with `_run_tool_loop` itself mocked to capture the actual `max_iterations` value it's invoked with (not just trusting a source-code read): `_try_groq()`/`_try_mistral()` both pass the general ceiling for ordinary chat (`ide_scoped=False`) and the much higher IDE ceiling when called from the IDE chat panel (`ide_scoped=True`).
- **D** — the exact reported scenario end to end: a realistic scripted 11-tool-call ecommerce build (fetch the skill doc, list the folder, create+write four files, a short self-review read pass, then a final answer) is reproduced failing under the *old* hardcoded cap of 5 (proving this really was the bug), and shown succeeding cleanly under the new IDE ceiling using exactly the round trips the script actually needed.
- Full regression pass: all 25 `dev_tests/test_*.py` files (24 pre-existing + 1 new) re-run under `DISPLAY=:99 QT_QPA_PLATFORM=offscreen`, all passing with no regressions; `python3 -m compileall .` clean; `ide/tests/run_all.py` re-run separately (213/213, unchanged).

### What's still honestly unverified
The fix is proven correct at the mechanical level — the real call sites pass the right ceiling, the loop itself behaves correctly at any ceiling, and the specific reported failure mode is reproduced and shown fixed with a realistic scripted scenario. What can't be verified in this sandbox, as always, is a live run against the real Groq/Mistral APIs with the user's actual workspace and actual model behavior — if a genuinely enormous build (a large multi-page app with many components) still exceeds even 40 round trips, that's a real possibility worth knowing about from actual use rather than guessed at further here; the ceiling can be raised again the same way if so.

## Part 22 — Build Protocol (Frontend/Backend/Storage) + inline "Permission" decision options in the IDE chat panel

User asked for a formal **Build Protocol**: any real development task in the IDE should be explicitly separated into Frontend, Backend, and Storage/Database layers, each followed through properly; `development_skill.md` should say code must be separated into individual files/folders, not dumped into monoliths; the user should be able to see where a build actually is at a glance; and the IDE's own "permission" mechanism (its pause-for-a-decision behavior) should offer concrete clickable options plus a free-text custom field — explicitly, "just like the way you [this agent] do and perform task," i.e. the same shape as this agent's own `ask_user` tool.

Four genuinely separate pieces were needed, all landing together as one coherent mechanism:

### 1. The Build Protocol itself (`development_skill.md`, new Section 6)
Any multi-layer development task is now explicitly separated into Frontend → Backend → Storage/Database, in that fixed default order (there's always something real and checkable at each step — a working UI before the API it calls, a working API before the schema under it needs to be permanent) unless the user's own request specifies otherwise. Each layer has its own specialized sibling skill doc, fetched on demand exactly the way Part 18's `ide_get_frontend_skill()` already worked — now joined by two new matching tools, `ide_get_backend_skill()` and `ide_get_storage_skill()`. Neither `BACKEND_SKILL.md` nor `STORAGE_SKILL.md` exists in this install yet (both are meant to be supplied by the user the same way `FRONTEND_SKILL.md` was); calling either tool right now returns a plain, non-crashing "not present yet, proceed with the general standard" message rather than an error — the reusable *pattern* is what's being delivered this turn, exactly as asked, with the content itself pending. File/folder separation is spelled out explicitly: one top-level folder per active layer, and inside each, files separated by concern (components/pages/styles, not one `index.html` with everything inlined; routes/controllers/models, not one file for a whole API).

### 2. A status checklist the user can actually glance at (`ide_report_build_status`)
A new tool, called at the start of each layer (`in_progress`), the moment it genuinely finishes (`done`), or if something stops it (`blocked`), each with a short one-line detail. It drives a small, persistent block embedded directly in the IDE chat panel's own log (not a new tab, not something to go looking for) — created once, then upserted in place on every subsequent call, so a long build never floods the conversation with duplicate status blocks. This is explicitly in addition to, never a replacement for, the normal narration beats — the checklist is for a glance, the narration is for the explanation.

### 3. Inline "Permission" decision options, directly in the chat box
This was the one piece that genuinely needed a design decision from the user before building (asked via `ask_user` this turn) — specifically *where* this UI should live. The answer: directly inside the IDE chat panel itself, not a new tab or sidebar view. A pending `{{AWAIT_DECISION}}` pause (Part 16's existing 2-minute-autonomy mechanism) can now also carry a companion control tag, `{{OPTIONS: "Option A" | "Option B" | "Option C"}}` (2-4 short labels, documented in `personality.md`), which the chat panel renders as clickable buttons right under the question — plus its own always-present text box underneath for a custom answer, mirroring exactly what this agent's own `ask_user` tool offers a user talking to it directly. Clicking a button (or submitting custom text) sends that exact text back through the identical path a typed message would take — completely indistinguishable from the user having typed it themselves. A brand new real message always dismisses a still-showing decision widget from the turn before, same reasoning the backend's own decision-tracker `cancel()` already uses.

This is deliberately IDE-chat-only: the floating circle is voice/spoken, where a clickable button has no meaning, so `personality.md` only ever tells the model to use `{{OPTIONS: ...}}` on that one surface — and as defense-in-depth, the circle's own reply-handling path still runs the tag-stripping function and discards the result, purely so the raw tag text itself can never get spoken aloud if a model ever emits it somewhere it wasn't told to.

### A real compatibility trap caught and fixed before it shipped
Wiring `options` through required `on_done`'s call signature in `agent_overlay.py`'s `_ide_chat_ask()` to grow from `(ok, text)` to `(ok, text, options)` — but five pre-existing test files (and, more importantly, any future caller) still use plain 2-argument callbacks. A naive `on_done(True, clean_reply, options)` call would have broken every one of them outright with a `TypeError`. The first instinct — a bare `try: on_done(True, clean_reply, options) except TypeError: on_done(True, clean_reply)` — was rejected on its own merits before it was ever shipped: it would have risked silently double-invoking (and so double-acting on) any callback whose own *body* happens to raise an unrelated `TypeError`, not just one that genuinely doesn't accept a 3rd argument. The actual fix is a small `_accepts_options_arg()` helper that inspects the callback's real signature up front (handling `*args`, bound methods, and non-introspectable builtins correctly) and decides the call shape *before* ever calling it — never attempting, and possibly repeating, a call that might have side effects. The same exact risk and the same fix shape applies to `agent_tools.notify_ide_chat()`'s handler, which grew the identical way.

A second, smaller trap: two existing tests (`test_agent_tools_ide.py`, `test_app_panels.py`) hardcode the exact total tool count Agent Mode exposes (`85`) as a regression guard against a tool silently vanishing or a new one silently going unregistered. Adding the three new tools (`ide_get_backend_skill`, `ide_get_storage_skill`, `ide_report_build_status`) correctly tripped that guard — exactly what it's there for — and both were updated to the new correct total, `88`, with the math spelled out in the check's own label the same way the original did.
